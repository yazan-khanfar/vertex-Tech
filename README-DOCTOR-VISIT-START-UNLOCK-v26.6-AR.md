# Smart Dental Clinic — تصحيح تفاعلات الزيارة الجديدة v26.6

## المشكلة الفعلية

في v26.5 كان قالب صفحة الزيارة يكتب `data-clinical-enabled="no"` عند عدم وجود سجل VISIT بعد. كود `visit-bridge.js` كان يفسّر ذلك مباشرة باعتباره `approved=true`، ويعطّل مربعات الفحص وأزرار الحفظ والتشخيص والإجراء والوصفة. أي أن زيارة لم تبدأ بعد عوملت خطأً كتقرير طبي معتمد.

## ما الذي تغيّر

- فصل حالة اعتماد التقرير الطبي (`data-report-approved`) عن حالة وجود زيارة بدأت فعلًا (`data-visit-id`).
- عدم تعطيل عناصر الواجهة في الزيارة الجديدة، وإتاحة كتابة الشكوى والتفاعل مع الخيارات.
- تغيير تسمية زر الحفظ في الزيارة الجديدة فقط إلى «بدء الزيارة وحفظ الشكوى»، مع الحفاظ على نفس شكله وموقعه؛ وبعد بدء الزيارة يعود إلى «حفظ كمسودة».
- عند الضغط على حفظ قسم سريري قبل بدء الزيارة، يظهر تنبيه يشرح ضرورة البدء أولًا بدل ظهور زر معطّل.
- إذا لم تُسجل العيادة وصول المريض، يظهر تنبيه واضح عند محاولة البدء؛ يبقى شرط تسجيل الوصول وتاريخ الموعد مطبقًا في Backend.
- عند اعتماد التقرير تبقى عناصر التعديل السريري مقفلة. الزيارة المكتملة دون تقرير معتمد تخضع للقواعد السابقة.
- لم تُعدل ملفات CSS أو سكيما PostgreSQL أو مسارات الحفظ أو صفحات أخرى.

## الملفات

- `views/doctor/visit.ejs`
- `public/doctor/assets/visit-bridge.js`

## اختبار عملي

1. حدّث المشروع من **v26.5** فقط باستخدام Patch، أو استخدم نسخة v26.6 الكاملة مع الاحتفاظ بـ `.env` والملفات الخاصة.
2. أعد تشغيل الخادم وافتح صفحة زيارة جديدة بعد عمل `Ctrl + F5`.
3. تأكد أن مربعات الفحص والتفاعلات قابلة للنقر.
4. أدخل سبب الزيارة واضغط «بدء الزيارة وحفظ الشكوى» **بعد تسجيل وصول المريض** وضمن يوم الموعد.
5. بعد إعادة تحميل الصفحة جرّب تحديد سن وحفظ حالته، وحفظ نتائج الفحص.
6. تأكد أن زيارة بتقرير معتمد لا تسمح بالتعديلات السريرية.

## الفحوص والحدود

- اختبار JavaScript تفاعلي بمحاكاة DOM للزيارة الجديدة (قبل وبعد تسجيل الوصول)، والزيارة الجارية، والتقرير المعتمد.
- اختبارات EJS في ثلاث حالات: لم تبدأ، جارية، مكتملة مع تقرير معتمد.
- الاختبار البرمجي لا يعادل اختبار حفظ فعلي على PostgreSQL لديك. لا يُعلن اكتمال تجربة المستخدم حتى تختبرها محليًا.
