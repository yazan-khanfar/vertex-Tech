# Smart Dental Clinic — التشغيل اليومي وربط بدء الزيارة v7

هذا التحديث مبني على **Smart-Dental-Clinic-Rejection-Reason-Merged-v6**، ويستخدم **الصفحات الأصلية** دون إنشاء صفحة جديدة أو تغيير ملفات CSS. لا يغيّر حسابات المرضى والأطباء أو مفاتيح MFA.

## ما أصبح مرتبطًا

- `/clinic/operations`: مواعيد **اليوم الحالي داخل العيادة النشطة فقط**، مع وصول المرضى، قاعة الانتظار، داخل العلاج، وعدم الحضور، من PostgreSQL بدل اسم/موعد تجريبي.
- المدير يستطيع تسجيل وصول المريض، أو تسجيل «لم يحضر» **بعد بدء وقت الموعد**؛ الإجراء ينحفظ في `BOOKING` ويظهر في سجل التدقيق. لا يمكن تسجيل وصول موعد غير مؤكد أو في يوم آخر.
- في `/staff/appointments`، موظف الاستقبال يستطيع تسجيل الوصول **فقط** عند وجود عضوية فعالة وصلاحيتي `appointments.view` و`appointments.manage`. من دون ذلك يبقى للعرض فقط.
- الطبيب يرى في `/doctor/appointments` زر «فتح الزيارة» بعد وصول المريض. لا يستطيع فتح زيارة لموعد آخر أو لطبيب آخر.
- `/doctor/visit?booking_id=...` يعرض معلومات المريض **الحقيقية** في قالب الزيارة الموجود، ويسمح للطبيب بتوثيق الشكوى والفحص وحفظهما في `VISIT`، ثم إنهاء الزيارة وتحديث `BOOKING`. كل حجز يرتبط بزيارة واحدة بفهرس `UNIQUE` الموجود أصلًا.
- منع إلغاء أو إعادة جدولة الموعد بعد تسجيل وصول المريض.
- عند الزيارة الحقيقية لا تُعرض نتائج أسنان أو إجراءات علاجية تجريبية كما لو كانت بيانات ذلك المريض.

## حدود هذه المرحلة

- ربطنا هنا سير الوصول وبدء الزيارة والشكوى والفحص وإكمال **الحالة**. بقية الأقسام الطبية من odontogram وخطة العلاج والإجراءات والوصفات والمرفقات واعتماد التقرير، وكذلك الفاتورة، **لم تُربط بعد** ولا تعتبر مكتملة. يظهر تنبيه في واجهة الزيارة الحية بذلك.
- صفحة الزيارة الحقيقية تعرض الأقسام المرتبطة فقط مستخدمةً تصميم البطاقات والأنماط الموجودة؛ لم تُحذف بنية التصميم الأصلية للقالب، وتبقى الأقسام غير المربوطة غير معروضة في سياق مريض حقيقي لعدم إظهار معلومات طبية وهمية.
- الاختبارات آلية ومن دون PostgreSQL الفعلي على جهازك؛ يجب تجربة التشغيل في المتصفح وعلى بياناتك.

## التركيب — مشروع كامل

1. خذ نسخة احتياطية من **المشروع وقاعدة البيانات**، وأوقف السيرفر بـ `Ctrl+C`.
2. افتح pgAdmin وحدد قاعدة `smart_dental_clinic` ثم Query Tool، وشغّل **مرة واحدة**: `db/migrations/003_daily_operations.sql`. التغيير فقط إضافة `BOOKING.Arrived_At` وفهرس؛ لا يحذف أي بيانات.
3. فك ضغط ZIP الكامل في مجلد جديد. `package.json` موجود في جذر الملف، دون مجلد متداخل.
4. انسخ `.env` السابق إلى جذر المجلد الجديد دون مشاركته أو تغيير مفتاح MFA مباشرة.
5. افتح CMD من المجلد، وشغّل:
   ```cmd
   npm install
   npm test
   npm start
   ```
6. افتح `/clinic/operations` بحساب مدير العيادة النشط.

## التركيب — Patch فقط

بعد النسخ الاحتياطي وتنفيذ SQL، فك ملف Patch ثم **انسخ محتوياته** إلى جذر مشروع v6 الحالي (بجانب `server.js` و`package.json`) مع استبدال الملفات المماثلة، ثم أعد تشغيل السيرفر. لا تنسخ مجلد الـPatch نفسه داخل المشروع.

## اختبار السيناريو

1. تحتاج موعدًا **مؤكدًا بتاريخ اليوم** في عيادة مدير الحساب. إذا لم توجد مواعيد اليوم، تظهر قائمة فارغة وهذا صحيح.
2. من `/clinic/operations` اضغط «تسجيل الوصول»، ولاحظ أن العداد يتحول إلى «بانتظار الطبيب».
3. من حساب الطبيب المرتبط بالموعد افتح `/doctor/appointments` ثم «فتح الزيارة»، واكتب شكوى فعلية غير تجريبية واضغط «بدء الزيارة».
4. احفظ فحصًا سريريًا فعليًا، ثم أكمل الزيارة وتأكد من ظهور «مكتمل» لدى الطبيب والعيادة والمريض.
5. جرّب موعدًا مؤكدًا آخر تجاوز وقت بدايته بدون تسجيل وصول، وتأكد أن «لم يحضر» يغيّر الحالة ويحفظها.
6. تأكد أن طبيبًا آخر أو موظفًا بلا صلاحية لا يستطيع فتح هذه العملية أو تغييرها.

## الأمان والتشغيل

- لا تعِد تشغيل ملف إنشاء DB الأصلية، ولا تشغّل Seeds، ولا تحذف البيانات.
- أبقِ ملفات `.env`، مفاتيح MFA، البريد وكلمات المرور على جهازك فقط.
- يظهر خطأ واضح إن لم يُطبَّق ترحيل SQL قبل تشغيل النسخة الجديدة.

## الفحص في بيئة التجهيز

نجحت 106 اختبارات Node.js بدون قاعدة بيانات خارجية، وفحص عرض 110 قوالب EJS والتحقق من الروابط. `npm install --offline` لم ينجح بسبب عدم وجود مكتبات cached؛ لذا لم نستطع إثبات تشغيل HTTP الحي أو اتصال PostgreSQL في بيئة التجهيز.
