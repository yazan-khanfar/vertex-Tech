# Smart Dental Clinic — Clinic Batch 3 / Phase A — v21

## الهدف
ربط **المالية والمخزون** بالـPostgreSQL على واجهات العيادة الأصلية من دون إضافة صفحات أو تعديل CSS. هذه مرحلة جزئية من الدفعة الثالثة؛ المختبرات والوظائف والتقارير الإدارية **لم تُربط ضمن v21**.

## ما تم ربطه

### /clinic/inventory
- عرض مواد العيادة من `sdc."INVENTORY_ITEM"` والكميات الحالية من `sdc."STOCK_MOVEMENT"` بدل الرصيد الوهمي.
- إضافة مادة برصيد افتتاحي اختياري، مع CSRF وتحقق من المدخلات ومنع تكرار الاسم/الوحدة ضمن العيادة.
- صرف مادة، توريد كمية، تسجيل تالف، وتسوية الجرد. لكل حركة سجل دائم باسم المستخدم ووقت التنفيذ.
- فحص الرصيد داخل معاملة SQL وقفل صف المادة قبل الخصم، فلا يسمح بصرف رصيد سالب.
- عرض آخر الحركات ضمن صفحات من 20 سجلًا، مع إحصاءات إجمالية وفلاتر محلية.

### /clinic/invoices
- عرض الفواتير التي تتبع العيادة فقط، بنودها الأصلية ومدفوعاتها الحقيقية وتفاصيل المريض والطبيب.
- عرض الحالات المالية المحسوبة من مبالغ البنود والدفعات؛ الاحتفاظ بحالات قاعدة البيانات `draft/issued/void` وعدم إنشاء حالة `paid` مخالفة للقيد.
- تسجيل دفعة في الفواتير الصادرة فقط، دون تجاوز المتبقي، ضمن معاملة وقفل صف الفاتورة. يدعم cash/card/bank_transfer.
- يُنشأ مبلغ الفاتورة من البنود الموجودة في DB؛ إصدار فاتورة جديدة أو تعديل البنود ليس جزءًا من هذه الدفعة.

### /clinic/settlements
- عرض التسويات الفعلية وعمولات الحجوزات المرتبطة بها ودفعات التسوية بالقراءة فقط. لا يجوز للعيادة اختراع دفعات تسوية؛ إدارتها تتبع سياسة المنصة.

## الأمن والحفاظ على الواجهة
- جميع المسارات بعد `guard('clinic')` وتتحقق من عيادة الجلسة عبر `clinicId(req)`؛ لا يُؤخذ رقم العيادة من الاستمارة أو URL.
- طلبات POST تتطلب `csrf_token` للجلسة، وتحدَّد هوية المستخدم من الجلسة، ويُضبط `sdc.user_id` على معاملة الكتابة كي تعمل قيود الصلاحيات في PostgreSQL.
- تستخدم SQL placeholders؛ الفواتير تمنع الدفع على مسودة أو فاتورة ملغاة وتمنع الزيادة؛ المخزون يمنع السحب فوق الكمية.
- لم تُعدَّل أي ملفات CSS، ولم تُنشأ واجهات جديدة. التغييرات في صفحات EJS الثلاث الأصلية وفي JavaScript تفاعلات UI فقط.

- `node tests/verify-structure.js`: نجح عرض 110 صفحة وفحص الأصول والروابط.
- `node tests/verify-routing-contract.js`: نجح مسار 110 صفحة وإعادة التوجيه.

**لم يمكن تشغيل npm test كاملًا أو اختبارات تكامل حقيقية على PostgreSQL** في بيئة التسليم لأن npm لم يتمكن من تنزيل الحزم. يجب اختبار الحفظ الفعلي والعرض والتصميم في المتصفح على جهازك قبل اعتماد v21 نهائيًا.

## التثبيت
- نسخة Merged v21: فكها في مجلد مستقل واحتفظ بنسخة `.env` السرية من بيئتك السابقة؛ لا تنشئ `MFA_ENCRYPTION_KEY` جديدًا لأن ذلك سيمنع فك أسرار MFA القديمة.
- نسخة Patch v21: فك محتوياتها فوق **v20 تحديدًا** مع الاحتفاظ ببنية المجلدات.
- في سطر الأوامر من مجلد المشروع:
```
npm install
npm test
npm start
```
- لا يوجد SQL Migration جديد لهذه المرحلة.

## اختبار القبول على بيانات تجريبية فقط
1. افتح `/clinic/inventory` وتأكد أن القائمة تعكس مخزون العيادة الحالي. أنشئ مادة واحدة وأدخل رصيدًا افتتاحيًا قدره 5.
2. اصرف 1، ثم حاول صرف أكثر من الرصيد المتبقي؛ يجب رفض المحاولة الأخيرة من السيرفر وعدم تسجيل حركة.
3. جرّب توريد 2 وتسوية الجرد، ثم افتح سجل الحركات وصفحاته.
4. افتح `/clinic/invoices` وتحقق من بنود الفاتورة والمدفوع والمديونية قبل إضافة دفعة.
5. لفاتورة *صادرة* لها رصيد، أضف دفعة جزئية؛ تحقق أنها حُفظت مرة واحدة ولم يزد المدفوع عن الإجمالي.
6. جرّب رابط دفع فاتورة من عيادة أخرى باستخدام حساب هذه العيادة؛ يجب أن يفشل.
7. افتح `/clinic/settlements` وتحقق من مطابقة الفترات والأرقام مع قاعدة البيانات.
8. راجع نفس الصفحات على الكمبيوتر والجوال للتأكد من التطابق البصري مع v20.

## مؤجل لما بعد هذه المرحلة
- المختبرات والحالات المخبرية (`/clinic/lab-cases` و`/clinic/lab-details`).
- الوظائف والمتقدمون (`/clinic/jobs` و`/clinic/job-applicants` و`/clinic/application-details`).
- الإشعارات والتقارير الإدارية وربط أي إجراءات معلقة لإصدار الفاتورة من زيارة الطبيب.
- اختبارات التكامل التي تعتمد على دور الطبيب تؤجّل وفق الاتفاق.
