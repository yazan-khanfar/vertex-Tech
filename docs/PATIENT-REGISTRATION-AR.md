# القسم الأول — تسجيل المريض وربطه بقاعدة البيانات

## 0. ما الذي تم تنفيذه؟

- **الواجهة:** `views/auth/register/patient.ejs` نفس التصميم، لكن النموذج يرسل إلى `POST /auth/register/patient` بدل إظهار تنبيه تجريبي.
- **معالج الطلبات:** `src/registration/router.js` — GET يعرض النموذج ورمز CSRF، وPOST يتحقق من الطلب ويستدعي الخدمة.
- **التحقق:** `src/registration/validate.js` — الاسم، تاريخ الميلاد، الجنس، البريد، الهاتف، كلمة المرور، تأكيدها والموافقة.
- **حماية:** `src/security/password.js` تشفير scrypt مع salt عشوائي؛ `src/security/csrf.js` رمز منع التزوير؛ `src/security/rateLimit.js` حد بسيط للمحاولات في خادم واحد.
- **قاعدة البيانات:** `db/pool.js` اتصال PostgreSQL؛ `src/registration/service.js` Transaction تبدأ بـ BEGIN وتنتهي COMMIT أو ROLLBACK.
- **البذر:** `scripts/seed-patient-role.js` يجهّز دور Patient بالنطاق System مرة واحدة (ولا ينشئ Super Admin).
- **عند النجاح:** يعود المستخدم لصفحة `/auth/register/success?role=patient`، **بدون تسجيل دخول تلقائي**؛ تسجيل الدخول لم يُربط بعد.

## 1. قاعدة البيانات التي اعتمدناها

ملفك المرفوع في `db/schema/001_Smart_Dental_Clinic_Original.sql` يعرّف **57 جدولًا، 406 عمودًا**، وليس إصدارًا سابقًا كان يضم 73 جدولًا. تم إبقاؤه دون تعديل. يتوقع إنشاء قاعدة بيانات **فارغة** بخادم PostgreSQL 15+ ثم تنفيذ الملف عليها **مرة واحدة فقط**: فهو يحتوي `CREATE SCHEMA sdc` ولا يحذف الجداول.

من **pgAdmin**: أنشئ Database باسم `smart_dental_clinic` (أو اسمًا تختاره)، ثم افتح Query Tool الخاص بها، وحمّل ملف SQL الأصلي ونفّذه على القاعدة الفارغة. انتبه أن أمر `CREATE DATABASE` لا يُشغل داخل `BEGIN`.

أو من PowerShell إذا كان `psql` مثبتًا ومعروف المسار:

```powershell
createdb -U postgres smart_dental_clinic
psql -U postgres -d smart_dental_clinic -v ON_ERROR_STOP=1 -f "db/schema/001_Smart_Dental_Clinic_Original.sql"
```

**لا تشغّل سكربت إنشاء الجداول على قاعدة موجودة فيها نفس Schema، حتى لا يفشل أو تتضارب البيانات.** لا يتم هنا تعديل أي جدول أو حذف بيانات.

## 2. إعداد الاتصال وتشغيل المشروع على Windows

افتح PowerShell داخل جذر المجلد الذي يحتوي على `server.js` و`package.json`:

```powershell
Copy-Item .env.example .env
```

ثم افتح `.env` محليًا وأدخل بيانات PostgreSQL الفعلية:

```dotenv
PORT=3000
DATABASE_URL=postgresql://postgres:YOUR_PASSWORD@127.0.0.1:5432/smart_dental_clinic
POLICY_VERSION=prototype-v1
```

إذا احتوت كلمة مرور قاعدة البيانات على أحرف محجوزة في روابط URL (مثل `@`, `#`, `%`)، ترمّز بشكل percent-encoding. لا ترسل ملف `.env` لأي أحد ولا ترفعه على Git. **قبل الإطلاق الحقيقي** غيّر `POLICY_VERSION` لإصدار مطابق لشروط وخصوصية منشورتين، واربط محتواهما بالواجهة.

نفّذ:

```powershell
npm install
npm run db:seed:patient
npm test
npm start
```

افتح الرابط:

`http://localhost:3000/auth/register/patient`

`npm run db:seed:patient` ضروري لأن SQL الأصلي ينشئ **جدول ROLE بدون سجل Patient جاهز**. لا تعبّئ `Role_ID` يدويًا؛ سكربت البذر يستفيد من `GENERATED BY DEFAULT AS IDENTITY`.

## 3. سيناريو الاختبار اليدوي

1. افتح صفحة التسجيل وتأكد من ظهور التصميم الأصلي وقائمة شروط كلمة المرور.
2. أدخل بيانات مختلفة حقيقية للاختبار، بريدًا لم تستخدمه، وتاريخ ميلاد سابقًا لليوم، وكلمة مثل `PatientPass123`، ووافق على الشروط.
3. اضغط "إنشاء الحساب". المفروض تنتقل إلى صفحة نجاح التسجيل؛ **ليس** إلى لوحة المريض مباشرة.
4. تحقق من الحفظ عبر pgAdmin Query Tool:

```sql
SELECT u."User_ID", u."First_Name", u."Last_Name", u."Email", u."Account_Status",
       p."Patient_ID", p."Date_Of_Birth", p."Gender", p."Blood_Type", p."Health_Notes"
FROM sdc."USER" u
JOIN sdc."PATIENT" p ON p."User_ID"=u."User_ID"
ORDER BY u."User_ID" DESC LIMIT 5;

SELECT "User_ID", "Policy_Type", "Policy_Version", "Accepted_At"
FROM sdc."USER_POLICY_CONSENTS" ORDER BY "Accepted_At" DESC LIMIT 10;
```

تأكد من حفظ سجل USER واحد، PATIENT واحد، وسجلَي موافقة للشروط والخصوصية لكل تسجيل. **كلمة المرور محفوظة كـ Password_Hash وليس كنص واضح**.

5. جرّب نفس البريد مجددًا بحروف كبيرة/صغيرة مختلفة: يجب عرض رسالة تكرار وعدم إنشاء حساب ثانٍ.
6. جرّب كلمة مرور ضعيفة، وميلادًا مستقبليًا، وعدم الموافقة: يجب رفض الطلب دون حفظ بيانات.
7. جرّب فتح النموذج ثم الانتظار حتى انتهاء CSRF، أو طلب POST بلا رمز: يجب رفضه. جرّب تحديث صفحة التسجيل والحصول على رمز جديد.
8. لإثبات Atomicity، اختبر عبر قاعدة منفصلة أو اختبار الموك، ولا تعبث ببيانات حسابات حقيقية.

## 4. القيود الحالية والخطوة التالية

- لا يوجد Backend حقيقي لتسجيل الدخول أو الجلسات أو MFA أو استعادة كلمة المرور أو تسجيل الطبيب والعيادة بعد. صفحاتها ظاهرة للتجربة فقط.
- حماية صفحات الأدوار وصلاحيات الوصول ستنفذ في مرحلة تسجيل الدخول. **لا تنشر هذا التطبيق في الإنتاج حاليًا** لأنه ما زال يعرض صفحات أدوار متعددة دون مصادقة فعلية.
- حد المحاولات الحالي داخل ذاكرة خادم واحد؛ للنشر الحقيقي يُستبدل بمخزن مشترك وحماية على مستوى البروكسي.
- لم يتم اختبار PostgreSQL أو المتصفح فعليًا داخل بيئة الإنشاء؛ الاختبارات الآلية الحالية على المدخلات والتشفير وCSRF والمعاملات باستخدام Mock، وعلى جميع قوالب الموقع وروابطه.
- لا توجد سياسة خصوصية وشروط استخدام رسمية مرفقة؛ قيمة `prototype-v1` صالحة لاختبار منطق التسجيل فقط، ولا تثبت موافقة قانونية على مستندات منشورة. لا تطلق التسجيل علنًا قبل ربط النسخ الرسمية.
- لم أغيّر تصميم باقي صفحات المشروع أو SQL الأصلي، ولم أضف `node_modules` للـZIP.

**الخطوة التالية بعد نجاح الاختبار على جهازك:** نراجع تسجيل الطبيب والعيادة، ثم تسجيل الدخول وMFA والصلاحيات.
