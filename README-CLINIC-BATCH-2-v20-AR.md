# Smart Dental Clinic — Clinic Clinical Batch 2 v20

الأساس: `Smart-Dental-Clinic-Staff-Permissions-Merged-v19.1.zip`.

## مهم قبل الدمج
- استخدم **v19.1 فقط** كأساس لتركيب الـPatch. النسخة الكاملة v20 مبنية عليه.
- انسخ `.env` محليًا من مشروعك الجاري، ولا ترفعه إلى Git أو تشاركه.
- خذ نسخة احتياطية من المشروع وقاعدة بيانات `smart_dental_clinic` قبل الاختبار.
- لا تشغّل `001_Smart-Dental-Clinic(3).sql` أو Seed أو إعادة إنشاء قاعدة البيانات.
- لا يحتاج التحديث إلى SQL جديد، ويحتفظ بترحيلات الجلسات/التشغيل اليومي/الدعوات القديمة.
- لم يُعدّل أي ملف CSS ولم تُنشأ صفحات واجهة جديدة.

## ما نُفذ في هذه الدفعة
1. `/clinic/treatment-plans`: عرض خطط العيادة الحقيقية فقط؛ الأطباء، المراحل، نسبة التقدم، الحالات، والفلاتر من بيانات SSR.
2. `/clinic/treatment-plan-details?id=...`: تفاصيل الخطة ومراحلها وموعدها المقبل للقراءة فقط. لا يسمح بالوصول إلى خطة عيادة أخرى.
3. `/clinic/recalls`: المتابعات التي اقترحها الطبيب في زيارات مكتملة؛ تمييز انتظار الحجز/التأخر/الحجز/الإلغاء.
4. `/clinic/new-appointment?follow_up_visit_id=...`: عند حجز متابعة من العيادة يتم التحقق من الزيارة الأصلية والمريض والعيادة، ثم ربط الحجز الجديد بحقل `Follow_Up_Of_Visit_ID` ضمن المعاملة نفسها. لا يمكن ربط زيارة ثانية أو زيارة من عيادة أخرى. قيد DB الحالي يسمح **بحجز متابعة واحد فقط لكل زيارة**، حتى لو ألغي؛ يلزم قرار تصميم لاحق لدعم إعادة الحجز بعد الإلغاء.
5. `/clinic/visit-checkout?visit_id=...`: عرض بيانات الزيارة المكتملة الأصلية، وسعر الخدمة المحفوظ وقت الحجز، وحالة التقرير والمتابعة. أزيل نموذج الفاتورة الوهمي، وتظل إدارة الفواتير ضمن صفحة الفواتير الموجودة.
6. `/clinic/doctor-report?visit_id=...`: إظهار ملخص بيانات الزيارة فقط **عند وجود اعتماد طبيب ومرجع التقرير المحفوظ**، للقراءة فقط. يتبع الزيارة والعيادة الحاليّتين.
7. `/clinic/patient-details` و`/clinic/operations`: روابط مباشرة لعرض الخطط والتقارير وإنهاء الإجراءات للزيارة الفعلية، بلا روابط سجلات تجريبية.
8. أُضيفت فلاتر عرض محلية لصفحات الخطط والمتابعات في `public/clinic/assets/app.js`؛ لا تجلب بيانات من JavaScript ولا تحفظها فيه.

## حدود المرحلة — لا نعتبرها مكتملة بعد
- النسخة المحفوظة والمعتمدة حرفيًا للتقرير الطبي (PDF أو ملف) **لا تُقدَّم من مسار تنزيل مقيّد بعد**؛ صفحة التقرير الحالية تُظهر ملخص الحقول المرتبطة بالزيارة وليست بديلًا للنسخة المجمدة.
- إصدار الفواتير والدفعات داخل `/clinic/invoices` وربط إحصاءات `/clinic/reports` ما يزال ضمن دفعة المالية والتقارير اللاحقة.
- إضافة التشخيص والإجراءات والأدوية واعتماد التقرير من **حساب الطبيب** لم يكتمل بعد؛ نعرض الموجود فقط، دون افتراض وجود بيانات.
- إعادة حجز متابعة مرتبطة بعد إلغاء الأولى تتطلب مراجعة قيد `UNIQUE` على `BOOKING.Follow_Up_Of_Visit_ID`.
- اختبارات القوالب والمنطق نجحت، لكن لم يتم الاتصال بقاعدة PostgreSQL الموجودة على جهاز المستخدم أو إجراء فحص بصري آلي كامل عبر المتصفح في بيئة التجهيز.

## خطوات التركيب
1. أوقف السيرفر (`Ctrl + C`).
2. إن اخترت الـPatch، فك ضغطه وانسخ **محتوياته** إلى جذر مشروع v19.1 حيث `server.js` و`package.json`، ووافق على الاستبدال. لا تنسخ المجلد الحاوي نفسه.
3. إن اخترت النسخة الكاملة، فكها في مجلد جديد، ثم ضع `.env` السابق في نفس مكان `server.js`.
4. من CMD داخل المشروع:

```cmd
npm install
npm test
npm start
```

لا تغيّر `MFA_ENCRYPTION_KEY` يدويًا أثناء الاختبار.

## اختبارات القبول الرئيسية
- من حساب مدير العيادة افتح `/clinic/treatment-plans`، وقارن خطط المريض الحقيقي بملف المريض. ينبغي عدم ظهور خطط عيادة ثانية.
- افتح `treatment-plan-details?id=<معرف فعلي>`، وتأكد أن المراحل والتقدم والتكلفة هي نفسها المخزنة في PostgreSQL. رابط خاطئ أو خطة عيادة أخرى يجب أن ينتج 404.
- افتح `/clinic/recalls` بعد تسجيل متابعة من الطبيب في زيارة مكتملة: ستظهر كـ«بانتظار الحجز» أو «متأخرة» حسب تاريخ الاقتراح.
- احجز متابعة من البطاقة عبر نفس صفحة `/clinic/new-appointment`. بعد الحفظ ينبغي أن تتغير الحالة إلى «تم الحجز». لا يجب أن يسمح بربط متابعة لزيارة مريض مختلف أو عيادة أخرى.
- من `/clinic/operations` افتح «إنهاء الإجراءات» لزيارة مكتملة، وتأكد من ظهور معلومات الزيارة الحقيقية مع روابط ملف المريض والفواتير.
- افتح التقرير من ملف المريض فقط لزيارة لديها تقرير معتمد؛ الزيارة غير المعتمدة يجب ألّا تعرض تقريرًا معتمدًا.

### الفحوص التي نُفّذت محليًا
- `npm test`: ناجح (بما في ذلك اختبار 110 قالب EJS و10 اختبارات جديدة لوحدة العرض السريري).
- لم تُعدّل ملفات CSS أو تنشأ جداول جديدة.
- `npm install --offline` لم ينجح في بيئة التجهيز بسبب غياب حزم ejs في ذاكرة npm؛ رغم ذلك نجح تشغيل `npm test` الخاص بالكود الموجود. على جهاز المستخدم نفّذ `npm install` بالشكل الطبيعي عند الحاجة.
